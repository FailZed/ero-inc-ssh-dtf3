# Первый связанный пакет: Селина, Дана и вход кафе

## Уточнение isolated candidate: фактическое прибытие

В копии `world-integration-2026-10-28/project` наблюдатель целей world/journey
теперь читает единый фактический `result.data.path`. Успешный прогноз или
переход к уже текущей точке с пустым path не увеличивает count и не записывает
unique-token. Считается только успешная команда с непустым пройденным путём
и действительным прибытием в указанную локацию. Время0/путь0 остаются допустимым
результатом чистого route_from(self,self), но не выполнением пешей цели.
Отдельных fallback-полей movement и кнопки ручного зачёта нет. Это уточняет
walk_check первой арки и остальные существующие journey-цели без нового schema.

Код original этим candidate-этапом не менялся. Ограниченный in-memory smoke
`project/.godot/world-geography-smoke/resident_leaf_smoke.gd` прошёл102проверки
безошибок, Godot4.7.2/Dummy, безautoloads иsaveIO. Проверены три исхода,
действительные journey-прибытия, пустой path безпрогресса/токена, однократная
память/флаг/XP иsnapshot restore. Визуальная проверка UI не проводилась;
естественная встреча NPC не гарантируется за заданное число минут.

28 октября 2026. **Контракт будущего ограниченного патча, не внедрение.**
Владение этого этапа: данный документ и
`data/world/design/story_bindings.json`. Игра, тесты и Git не запускались.
Новый сценарий Google Docs не прочитан; имена и детали новых жителей остаются
предложениями. В локальном `chapter_one.dtl` имя Мира занято, поэтому здесь
Селина Вейл, 29; продавец — Дана Керн, 41. Другие жители и две другие арки
из первого дизайн-пакета в этот патч не входят.

После подготовки контракта координатор отдельно разрешил и применён только
один подтверждённый runtime-fix: нулевой XP больше не вызывает `gain_xp`,
а каталог отвергает отрицательную, дробную и нечисловую награду. Добавлен
профильный сценарий в `tests/gameplay/run_sandbox.gd`, он **не запускался**.
Описанные ниже жители, граф, назначения и встречи остаются отдельным планом.

Следующим отдельным разрешением координатора в `npc_stories.gd` добавлено
чтение явного `npc.biography.story_arc`. Строка задаёт существующую арку,
пустая строка означает отсутствие истории. Неверный тип/ссылка и расхождение
с уже начатой аркой отклоняются с `invalid_personal_story_binding`;
`blocked/execute` для пустого назначения возвращают `personal_story_unassigned`,
`present` возвращает пустой Dictionary до обращения к узлам. Генерация,
`assign_created`, UI и hooks этим узким этапом не внедрены. Для NPC без нового
поля сохраняются текущие именованные/общие правила; замена общего hash-выбора
относится к отдельному A06, а не служит запасной ветвью явного назначения.

Также отдельно закрыты UI-callers: personal-story окно завершает обновление
для пустого view и исчезнувшего NPC, скрывая старый портрет; карточка жителя
не предлагает личную историю при отсутствии арки, журнал пропускает пустой
view до доступа к полям. Неожиданно пустой ответ у назначенного жителя показан
как ошибка и записан в диагностику, не подменён придуманной аркой. Это только
guards в двух существующих UI-файлах, без новой компоновки, тестовых запусков
или создания жителей.

Цель: в существующем свободном мире появляются две связанные бытовыми делами
взрослые жительницы. Игрок знакомится обычным способом, может добровольно
помочь с указателем кафе, возвращается позже и замечает результат. Всё
обслуживают существующие население, `npc_stories`, отношения, календарь и
снимок мира. Второй runner, отдельная симуляция и новые режимы диалога не нужны.

## Предлагаемая небольшая последовательность патча

### 1. Сначала принять пространственные и карьерные зависимости

Целевые ID из нового графа: `south_trade_street`, наружный
`riverside_cafe_front`, зал `riverside_cafe`, дворы `residential_district`,
частные `city_resident_home_selina` и `city_resident_home_dana`.
Географ добавил двум домам выходы по две минуты к дворам, владельцев
`resident_cafe_shift_lead` и `resident_south_grocer`, без меток и доступа
игрока по умолчанию. Это согласованный дизайн, а не уже работающий каталог.

NPC-рутер передаёт собственный actor ID. Запрет входа игроку не должен
запретить хозяйке вернуться домой. `bedroom`, дом Асуки, аптека и подъезд
Оливера здесь не используются. Река настоящего времени не заменяет море
детского воспоминания.

Профессии — открытая зависимость владельца карьер: текущие `cafe_orders`
работают в кафе 120 минут, `shop_assistant` — в `north_shops` 180 минут.
Для Даны нужна южная торговая точка; для Селины — именно кафе. Должен появиться
явный авторский выбор профессии/рабочего места через согласованный контракт
карьер. Не править `npc.mind.employment` после инициализации и не маскировать
двухчасовую смену как семь часов настоящего труда. Образцы schedule в JSON
показывают текущую форму данных; часы рабочего дня согласуются с этим владельцем.

### 2. Создать двух жителей через существующий генератор

Предлагаемые новые рабочие файлы патча:
`data/world/city_residents.json` и `scripts/gameplay/city_residents.gd`.
Это данные и маленькая утилита создания, не движок историй.

В `main_simulation._init()` после применения принятого городского графа
утилита явно **merge**-ит два шаблона в `catalog.npc_templates`.
Данные пары входят в проверяемый каталог/его hash. В `gameplay._start_npc_life()`
перед включением агентности вызываются обычные `simulation.command()`:

```json
{"module":"social","operation":"generate","args":{"id":"resident_cafe_shift_lead","template":"city_cafe_shift_lead","name":"Селина Вейл","age":29}}
```

Второй вызов аналогичен для `resident_south_grocer`/`city_south_grocer`.
Готовые примеры шаблонов лежат в `story_bindings.json`; поля `home`, `schedule`,
`role`, `occupation`, `education`, `cohort` соответствуют реальному генератору.
Итоговые вид и графика берутся из существующего каталога внешности, без новой
якобы утверждённой модели MDRG и без канонизации вида новых персонажей.

Жительницы — отдельная авторская городская пара сверх настраиваемой случайной
популяции, как нынешние сюжетные NPC отделены от random population. Это нужно
описать при внедрении, а не молча отнять два случайных слота у настройки count.
В песочнице это городские взрослые, а не импорт сюжетного состава первой главы.

До команд проверить оба ID, шаблона, дома, рабочие места и маршруты.
Новый `npc.biography.city_cast_id="first_trade_loop"` устанавливается hook-ом
создания в общей транзакции. При повторном входе начатой инициализации можно
использовать только точно помеченного актёра; чужой конфликт зарезервированного
ID — ошибка. `world.flags.city_pair_seeded=true` выставляется после обеих
успешных команд. При восстановлении снимка не создавать пару заново и не
исправлять её отсутствующие записи автоматически.

При создании **нет** `social.contact`, подарков, доверия к игроку и наград.
Соседство по работе не означает дружбу: автоматическую начальную близость
через ручную правку bonds или старый `legacy_change` в этот пакет не добавлять.
Отношения могут складываться при реальных пересечениях.

### 3. Назначать арку один раз, без hash-подмены

Добавить в каталог `npc_stories.json`:

```json
{
  "npc_story_bindings": {
    "asuka":"asuka", "oliver":"oliver", "ellie":"ellie",
    "resident_cafe_shift_lead":"rear_door_notice",
    "resident_south_grocer":""
  },
  "npc_story_assignment": {
    "by_goal": {"community":"neighbor", "creativity":"maker", "career":"newcomer", "mastery":"maker", "wellbeing":"newcomer"},
    "default_arc":"newcomer"
  }
}
```

Новая маленькая `npc_stories.assign_created(ids)` получает созданные NPC,
выбирает авторскую запись либо явное правило по **начальной** `biography.goal`
и записывает `npc.biography.story_arc`. Оно сохраняется вместе с NPC. Для Даны
пустая строка — намеренное отсутствие собственной арки первого пакета.

В `main_simulation.after_command()` вызвать её только для
`population/generate → result.data.ids` и `social/generate → [result.data.id]`.
Это остаётся в транзакции `Simulation.command`: ошибка откатывает создание,
назначение, RNG и события. `social.gd` и `population.gd` для данного hook
редактировать не требуется. Новые дети/акторы, создаваемые прямым внутренним
генератором вне этих двух команд, не получают молча случайную арку; их будущую
авторскую привязку назначает владелец соответствующей системы отдельным этапом.

Готовая часть: если `npc.biography.story_arc` есть, `arc_for()` читает именно
его и проверяет ссылку. Ни пустая, ни неверная явная запись не попадают в hash.
`state_error()` проверяет, что начатая `story.arc` равна явному назначению NPC.
Никакого нового назначения при `present()`, `start()` и загрузке.

Оставшаяся отдельная задача A06: заменить механизм выбора для обычной категории
при создании. До её назначения NPC **без** явного поля сохраняют действующий
выбор известных героев и общих арок. Три общие арки останутся контентом при
будущей замене; они не подменяют ошибку у явно назначенного авторского NPC.

Для пустого назначения `present()` возвращает `{}`. Два потребителя нужно
держать согласованными: `game_screens.gd` уже скрывает кнопку личной истории
для пустого arc_for и пропускает пустую запись журнала;
`personal_story_window._refresh()` уже обрабатывает пустой view до чтения `title`.
У неизвестного/исчезнувшего NPC очищается тело, скрывается портрет и вызывается
end_update. У unassigned жителя показывается честное отсутствие личной истории.

### 4. Обычное знакомство и реальные встречи

Не использовать `gameplay.talk_to_story_npc()` для этой пары: этот метод
предназначен для толпы управляемой первой главы. В свободной игре уже есть
обычное `npc_dialogue`, реальные последствия тем и обмен контактами через
`conversation_room._contact()` → `social.contact`.

Проверки `contact`, trust≥5, grievance<10 сохраняются. Контакт не равен доверию;
просмотр профиля, повторное чтение реплики и создание NPC ничего не повышают.
Число 22 минуты для нашей петли относится к уже знакомой доступной Селине,
не включает знакомство/дорогу к кафе и не обещает немедленного старта новой игры.
Обычное общение изменяет отношения по действующим правилам и ограничениям повторов.

Для Селины после смены предложено **добровольное заранее выбранное личное
обязательство**: перерыв у `riverside_cafe_front`, допускающий короткий разговор.
У Даны своё краткое окно у кафе; её присутствие не является условием завершения
арки. Это ещё не готовые строки schedule. Обычная необязательная строка не
гарантирует прибытие, а простое добавление `mandatory=true` создаёт конфликт
с календарём и может ложно заблокировать разговор. Поэтому JSON хранит эти
намерения отдельно от образцов рабочего расписания. До внедрения владелец
планировщика согласует их семантику, медицинский приоритет, дорогу и следующую
смену; менять существующий runtime встреч этим этапом не разрешено.

В `npc_stories.blocked()/execute()` до `_cancel`/pin добавить проверку:

1. NPC действительно рядом и не едет; граница контакта, активный partner/receiving,
   `npc_planner.active_owner()` и действующая `availability(id,true)` допускают разговор.
2. Выбранные минуты известны из проверенного choice, а не из произвольного args.
3. Обычный `calendar.conflict(id, npc.location, minutes)` не видит препятствий.
   Разрешено игнорировать **одно** текущее окно recreation только при том же месте,
   реальном времени внутри него и завершении разговора до его конца. Передаётся
   его абсолютный `window.start` как `ignore_schedule`; работа/учёба, следующая
   дорога, встреча, медицина и уход не игнорируются.

Нельзя делать исключение «эта история важнее календаря» или снимать медицинское
задание ради записки кафе. Pin держит человека только на время выбранной реплики,
не на всю прогулку героя. Если после двух переходов Селина ушла, прогресс
сохраняется, а итог обсуждается при следующем физическом пересечении.

### 5. Одна настоящая цель и два исхода

Граф из шести узлов уже преобразован в фактическую форму `title/nodes/text`,
`choices.{id,text,next,minutes,energy}`, `goal/done`, `ending/xp/bond` в
`story_bindings.json::npc_stories_catalog_fragment`.
Цель после принятия:

```json
{"module":"world","operation":"journey","locations":["south_trade_street","riverside_cafe_front"],"unique":true,"count":2}
```

Старый `global_map` в этой арке не сохраняется адаптером. Успешные переходы
должны завершиться в двух разных указанных местах. Неудачная дорога, открытие
карты и повтор одного места не закрывают её. Ранние прогулки до принятия не
засчитываются автоматически.

Для концовок добавить маленькое `node.effects` и вызывать существующее
`sim.apply_effects()` **в том же** terminal-переходе под однократным guard:

```json
{"kind":"flag","id":"cafe_notice_resolution","value":"clear"}
```

`clear_end→clear`, `oral_end→oral`, `declined→declined`. Первоначально валидатор
историй принимает для этого расширения только корректные flag-эффекты из
разрешённого набора; произвольный исполняемый язык команд в данные не добавляется.
Постоянный итог: `story.ending` плюс проверяемый `world.flags.cafe_notice_resolution`.
`state_error()` отвергает несоответствие значения завершённой арке. До завершения
этот флаг отсутствует; три независимых boolean, способных противоречить друг другу,
не нужны.

**Отдельно исправленная подтверждённая проблема:** `execute()` раньше всегда
вызывал `character.gain_xp`, а `character.gd:14` отвергает amount≤0.
Из-за этого `declined.xp=0` откатывался целиком. Теперь gain_xp вызывается только
при положительном значении; `catalog_error()` отвергает отрицательную,
дробную или нечисловую награду с `invalid_personal_story_xp`. Профильный сценарий
добавлен, но не запускался. Нулевой опыт остаётся допустимой завершённой концовкой:
`status=completed`, `ending=declined`, `rewarded=true` означает «исход уже
применён», а не обещание фактически выданного опыта.

`social.remember(...,"personal_story",{arc,ending})` и существующее событие
завершения создаются один раз. Сбой эффекта, опыта или валидации откатывает весь
переход штатной `Simulation.command`, а не оставляет половину изменения.

### 6. Повторный визит — чистый запрос

Новая `npc_stories.revisit(id)` выбирает только строковый ключ из небольшой
таблицы `npc_story_revisits`: история завершена, герой у наружного кафе,
наступил следующий игровой день относительно `story.updated`, известен исход.
Ни команд, ни `remember`, ни изменений World/RNG/опыта при запросе нет.

- Для ясной записки при настоящем присутствии Даны: она убирает ящик.
  Без Даны — только описание уже свободного прохода.
- Для устного решения при присутствии Селины: она показывает посетителю дверь.
  Без Селины — старая записка и отсутствие окончательной переделки.
- Для отказа при присутствии Селины: она сверяет свои записки и здоровается.
  Мы не заявляем, будто она сейчас возвращается из лавки, не проверив реального пути.
- В другом месте и сразу после завершения — пустой результат.

Показать это коротким дополнением существующего personal-story view. Не создавать
новый модальный экран и не запускать историю заново. Наблюдение обычного места
можно подключить UI-исполнителю к его предметной панели тем же чистым запросом
следующим маленьким изменением. В первом патче достаточно существующего окна.

### 7. Локализация и сохранение

В новой арке поля остаются `title/text/instruction/choice.text`, но содержат
стабильные `world_story.*` message IDs. Параллельных `text_key`-полей и веток
«новый формат/старый формат» в runtime нет. В данных контракта приведены
RU/EN-строки именно для этого пакета.

Добавить их в текущие `GameSession.TRANSLATIONS`; на границе отображения
использовать `GameSession.localize(str(value))` в personal-story окне, названиях
карточек журнала и `Presentation.event_text()` для двух событий истории.
`GameSession.language_changed` обновляет открытое окно. Симуляция сохраняет
ID узлов/выборов и message IDs, а не локализованные копии текста и не язык
как условие успешности команды. Новый перевод не создаёт второй источник
состояния. Нынешняя переводческая цепочка Dialogic timeline не читает автоматически
наши JSON-строки — просто положить их рядом с Dialogic CSV недостаточно.

`Simulation.export_snapshot()` уже содержит полный `state`, seed/state RNG и
`catalog_hash`; `Gameplay._checkpoint()` кладёт его в сериализуемый `World`.
Назначение в biography, начатая/завершённая арка, флаг исхода, реальное положение
и расписание автоматически входят в этот снимок. Не нужен новый формат слотов.
В контрактах есть пример **фрагмента**, не готового для загрузки целого снимка.

При восстановлении только валидация: NPC существует; назначенная арка совпадает;
история/прогресс и время правдоподобны; completed соответствует ending/rewarded;
флаг исхода согласован. Не восстанавливать флаг повторным выполнением концовки,
не начислять повторную награду и не перегенерировать NPC. Текущий MAIN_SCHEMA
наблюдался равным10, но итоговый номер при общей интеграции выбирает координатор
после чтения актуального кода. Миграции, легаси-ветви и переписывание слотов
не добавляются; несовместимые schema/catalog_hash отклоняются.

## Критерии завершения будущего патча

Это список конкретных ожидаемых исходов, не утверждение о выполненных тестах:

- Из story и sandbox при открытии свободного города создаётся ровно одна пара;
  перед прологом, после загрузки и повторного чтения журнала новые NPC не появляются.
- Дана не получает hash-шаблон. Шесть прежних арок не исчезают из каталога;
  новые обычные жители получают сохранённое явное назначение при создании.
- Без знакомства/доверия история не стартует; просмотр не меняет это.
- Селина приходит ногами и может быть занята. Разговор не ломает уход, медицину,
  рабочую смену или следующую встречу. Прогулка героя не удерживает её на месте.
- Две успешные разные поездки закрывают цель один раз. Поздний возврат сохраняет
  прогресс до следующей реальной встречи.
- Все три концовки, включая нулевой опыт при отказе, завершены без повторной награды.
  Отказ не ухудшает отношения и не закрывает обычное обслуживание.
- Повторный визит выбирает присутствующий/предметный вариант; чтение не меняет
  состояние или RNG. Отсутствующая Дана не произносит реплику из другого района.
- Снимок после первого перехода и после завершения продолжает тот же узел/исход,
  без пересоздания людей, флагов и наград. Язык переключает текст, не состояние.

Фактически выполнено здесь: чтение перечисленных исходников, сверка текущей
схемы, оформление ограниченного контракта и отдельно разрешённый fix нулевого
XP в `scripts/mechanics/npc_stories.gd`. В `tests/gameplay/run_sandbox.gd`
добавлен сценарий отказа с0XP, однократной памятью, повторным нажатием и
отказом каталога для отрицательной/дробной/нечисловой награды. Эти сценарии
не запускались; нативные окна, сохранения и Git не трогались.

Дополнительно выполнена узкая поддержка явного поля в том же runtime-файле
и добавлен `_test_explicit_personal_story_binding` в тот же профильный runner:
заданная/пустая/неверная привязка, снимок, запрет подмены начатой арки,
неизменность state/RNG при чтении/отказе и сохранение правил других категорий.
Новый профильный сценарий также **не запускался**. Базовая validation уже
требует `biography` как Dictionary и не запрещает дополнительные поля;
правка общего schema/валидатора для строки не понадобилась.

Последний маленький UI-пакет затронул только
`scripts/ui/gameplay/personal_story_window.gd` и personal-story участки
`scripts/ui/gameplay/game_screens.gd`. Тесты на простые guards не добавлялись;
выполнено только чтение исходников/правок. Новая пара и её арка всё ещё не

будущей общей интеграцией.
